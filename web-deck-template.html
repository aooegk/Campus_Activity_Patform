03　找个搭子

痛点 → 目标

找不到搭子，满员就只能放弃

痛点 1 · 找不到人

想打球、想自习、想拼桌游，身边人不一定有空，活动常常凑不齐人而取消。

痛点 2 · 满员就乱

名额满了只能在群里问，谁先来、谁替补全凭口头，退出一个名额也补不及时。

目标

发布活动 → 报名 → 满员自动候补 → 有人退出自动递补 → 限时确认，超时顺延。

衡量标准：人数不能算错，排队不能插队，邀请不能一女二嫁。

约30秒：痛点有两个，找不到人和满员混乱。我们的目标是一条完整链路：发布、报名、候补、递补、限时确认。最后那句就是验收标准，人数、排队、邀请三样都不能错。

04　找个搭子

这为什么是数据库课设

页面不难，难的是并发下的数据一致

有效占用 ≤ 上限

有效占用 = 正式人数 + 未过期待确认邀请数，两者之和永远不能超过上限，这条不变量由事务保证，不是事后统计。

防重复 · 防超员

同一活动同一用户只有一条当前参与记录，唯一约束是最后一道防线；多人同时报名也不能冲破上限。

邀请只能有一种终态

接受、拒绝、超时、失效互相竞争，条件更新 WHERE status='PENDING' 只让先到者改状态，后到者影响 0 行，只能读回当前终态。

候补排序要稳定

按入队时间排，时间相同按记录编号排，即 ORDER BY queued_at, id；退出重进要重新排队，不保留原排名。

约35秒：这是我们选题最像数据库课设的地方。四个规则都不能只靠前端按钮挡。报名先在一个事务里用 SELECT … FOR UPDATE 锁住活动行，再算正式加预留，算完才写参与记录，并发报名排队进事务，锁一放、后来的重算一遍，所以冲不破上限。邀请接受和超时扫描抢同一条记录时，条件更新只让先到的改状态。后面讲表怎么设计来保证这四条。

05　找个搭子

数据模型：6 张表

对应需求文档第 4 章，关系和约束先定死

app_user 用户

id / account 唯一
nickname / role / status

activity 活动

organizer_id → user
capacity / deadline / start / end

participation 参与

activity_id + user_id 唯一
FORMAL / WAITING / INVITED

invitation 邀请

participation_id → 参与
PENDING / ACCEPTED / 超时等
(status, expires_at) 组合索引

notification 通知

user_id + event_key 唯一
type / content / read_at

feedback 评价 P2

participation_id 唯一
score 1–5 / content ≤ 500 字

关系：用户 1–N 活动；用户 N–M 活动（经参与记录）；参与 1–N 邀请历史，但同时只能有一个待确认邀请。

约35秒：六张表，用户、活动、参与记录、邀请、通知、评价。约束分三层：外键保证引用完整，CHECK 约束卡住容量、时间顺序和评分范围，唯一约束防重复写入。索引也有分工：邀请表上对状态加过期时间建组合索引，超时扫描按状态和过期时间走索引而不是全表扫；通知按用户加事件键唯一，同一事件只发一条。下一页是从库里反向生成的 ER 图，线和基数可以对照着看。

数据模型：ER 图

从正在运行的 PostgreSQL 数据库反向生成，6 张表、外键与基数一一对应

读法：下划线是主键，*_id 是外键；线上的 1 / 0..N / {0,1} 是基数。

1 个用户可组织 0..N 个活动；1 个活动对应 0..N 条参与记录；1 条参与记录对应 0..N 条邀请历史；评价与参与记录 1 对 1。

约40秒：这张 ER 图不是手画的，是用 ERAlchemy 连上正在运行的 PostgreSQL 反向生成的。重点看三条线：用户到活动是一对多，活动到参与记录是一对多，参与记录到邀请是一对多，评价到参与记录是一对一，因为评价表上参与记录编号唯一。

事务 / 行锁 / 唯一约束

  • 国内可直连：Maven 走阿里云镜像，npm 走 npmmirror；前端打包进后端，不依赖国外 CDN。
  • Windows 演示：装好 JDK 17 和 PostgreSQL 后，双击 run.bat 启动，浏览器打开就能操作。
  • 数据库用法：报名、递补、超时三条写路径都落在事务里：读数先锁行，写数用条件更新，扫描只处理到期的 PENDING 邀请。
  • 配置分离：端口、数据库连接、确认窗口、扫描周期都放配置文件，不写死路径和密码。
约35秒：路线是 Vue 3 加 Spring Boot 3 加 PostgreSQL，都是主流方案。数据库这边重点讲用法：PostgreSQL 不只是存数据，容量不变量靠事务加行锁保证，邀请终态靠条件更新保证，超时靠组合索引加定时扫描保证。补充两点：一是依赖源全部换成国内可直连的镜像，二是演示版把前端打包进后端，Windows 上只要有 JDK 17 和 PostgreSQL 就能跑。

09　找个搭子

验收标准：先说好怎么算通过

来自需求文档第 5 章，不是临场发挥

  • 20 人同时报名，上限 4 人：最终恰好 4 名正式，其余为候补，行锁串行化加唯一约束兜底。
  • 同一账号并发提交多次：只产生一条有效参与记录。
  • 确认与超时同时到达：同一邀请只出现一种终态，条件更新抢占，不重复分配名额。
  • 超时后：原邀请失效并顺延，过期确认接口直接拒绝，不等扫描任务。
  • 重启后：已提交的参与记录不丢失，定时任务补扫未处理邀请。
约30秒：验收标准提前定好，写进需求文档第五章。这些不是只跑一遍演示，而是数据库层面的保证：行锁加唯一约束挡并发超员，条件更新挡终态竞争，超时扫描加过期判定挡顺延遗漏，重启后已提交记录不丢、扫描补处理。五条按标准逐项通过，才算核心流程跑通。
